## Changes from the fifth edition

The Global preface offers two parallel core routes, Verilog and VHDL. The authors recommend teaching the same design method in the chosen language and present SystemVerilog as an optional extension of the Verilog route. Chapters 1–8 keep the progression from representations through RTL, followed by labs in Ch. 9, symbols in Ch. 10 and the semiconductor appendix at p. 640. ## Language-neutral reading route

For each design, write the input and output contract, including widths and allowed values. Derive a truth table or state transition table. Model the circuit in one language, then write a bench that drives each input and observes the output at a defined time. Use the same vectors and observation points when checking the companion pair. The companion uses modern SystemVerilog and VHDL-2008.

| Design step | Verilog book reading | VHDL book reading | Modern companion pairs |
| --- | --- | --- | --- |
| Describe a Boolean function and read a truth table | §§3.9–3.10, pp. 137 and 154, Verilog modules, assignments and tabular primitives | §§3.9–3.10, pp. 137 and 154, VHDL entity, architecture, and table-to-model treatment | [Majority and minimization](../examples/README.md#boolean-logic) |
| Model combinational logic, then drive and sample it | §§4.12–4.15, pp. 205–245, Verilog modeling, a testbench and simulation | §§4.12–4.15, pp. 205–245, VHDL modeling, a testbench and simulation | [Arithmetic and mux](../examples/README.md#combinational) |
| Describe a clocked transition and check the next state | §5.6, p. 291, Verilog sequential models. §6.6, p. 372, registers and counters | §5.6, p. 291, VHDL sequential models. §6.6, p. 372, registers and counters | [Sequence detector](../examples/README.md#sequential) and [loadable counter](../examples/README.md#shared-binary-contract) |

For the optional Verilog extension, read §8.13, p. 549, on selected SystemVerilog types and process constructs. ## Comparing the two companion languages

| Design question | SystemVerilog | VHDL-2008 |
| --- | --- | --- |
| What values can the interface carry? | `logic` is a four-state data type. A `logic` variable holds an assigned value. A net such as `wire logic` resolves its drivers. | `std_logic` is a resolved nine-valued subtype of `std_ulogic`. Its domain includes uninitialized and weak drive values. |
| How do assignments update a combinational output? | Use a continuous assignment or `always_comb` with an assignment on every path. | Use a concurrent signal assignment or `process(all)` with an assignment on every path. |
| When is a register result visible? | In `always_ff @(posedge clk)`, nonblocking `<=` schedules an update. Sample after that update. | Inside `if rising_edge(clk) then`, signal `<=` schedules an update and a variable assignment takes effect immediately. Sample signal outputs after the required delta cycles. |
| How does the bench signal a failure? | The companion samples after settling and uses case inequality (`!==`) with `$fatal(1, ...)` so unexpected unknowns fail a binary check. | The companion samples after settling and uses a sequential `assert ... report ... severity failure`. The runner's `--assert-level=error` makes those failures terminate the regression. |

Compare settled 0/1 behavior first. If a model drives or observes unknowns, high impedance or weak values, define which values correspond and which drivers participate before comparing the results. See the [companion bench behavior](../examples/README.md#shared-binary-contract). [Global modeling sections](SOURCES.md#e6-global-body)
